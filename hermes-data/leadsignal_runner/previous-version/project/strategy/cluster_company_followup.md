# Vérification ciblée — Cluster / vélocité d'offres tech

Ce protocole complète la découverte Apify du seul signal `tech_job_velocity_cluster`. Il s'applique aux nouveaux lots autorisés ; ne pas modifier silencieusement un batch déjà figé. Les critères ICP et les seuils effectifs proviennent du snapshot du batch.

1. La recherche principale identifie les employeurs : une seule offre pertinente suffit pour conserver une piste. Ne pas rejeter une entreprise parce que cette page contient moins de trois offres. Garder le signal pending jusqu'à la vérification ciblée ; le seuil de trois offres datées concerne la publication finale. Qualifier d'abord l'employeur réel selon l'ICP. Conserver les offres et les `company_urn` déjà sauvegardés. Un cabinet qui annonce pour un client inconnu n'est pas l'employeur de ce client.
2. Pour chaque employeur ICP `pass`, relire les offres existantes de cet employeur dans les lots et les observations précédentes. Ne lancer aucune recherche payante si les preuves existantes suffisent déjà. Vérifier l'absence de cluster identique déjà publié.
3. S'il manque des offres, appeler `apimaestro/linkedin-jobs-scraper-api` pour **un seul** `company_id` vérifié par appel. Utiliser `cluster_company_followup.json` comme modèle : `keywords` vide, France, tri récent, `date_posted=month`, `limit=10`. Ne pas concaténer les identifiants : la limite de résultats est commune et une entreprise volumineuse monopolise la réponse. Ne pas mettre de longue expression `OR` dans `keywords` : l'essai a renvoyé une réponse vide.
4. Utiliser uniquement research_request.py pour l'appel ciblé. Le helper effectue lui-même la réservation atomique via leadsignal_reserve_cluster_company_call et la journalisation. Ne pas réserver ni journaliser manuellement une deuxième fois. Conserver et réutiliser run_id, dataset_id, raw_results et qualification_report. Réconcilier une réservation incertaine avant toute nouvelle requête. Ne pas utiliser son ID comme source_lot_id d'un lot primaire.
5. Filtrer chaque réponse par employeur réel, identifiant de l'offre, métier tech/data/produit, date d'origine et statut de l'offre. Les termes dans la description ne suffisent pas : le poste lui-même doit correspondre. Écarter les copies d'une même vacance et les missions freelance hors périmètre configuré. Vérifier les dates dans la fenêtre du snapshot et la complémentarité des rôles. Réutiliser `job_evidence.py` pour contrôler les preuves structurées ; ses booléens doivent correspondre à des éléments réellement observés.
6. Arrêter les appels ciblés dès que le seuil du snapshot est prouvé. Sinon, avancer `page_number` pour cette entreprise jusqu'à trois pages au maximum, ou jusqu'à la limite de budget/délai. `date_posted=month` couvre moins que la fenêtre de 60 jours du signal ; si le premier mois ne donne pas le seuil, compléter à partir des preuves déjà sauvegardées, puis consulter sans `date_posted` si le budget le permet et filtrer les dates reçues sur la fenêtre exacte. Ne pas traiter les pages non consultées comme examinées. Garder `pending` quand la vérification reste incomplète.
7. Si l'ICP et le signal sont `pass`, contrôler le doublon d'événement puis publier **une** opportunité pour l'employeur. Avant la publication, écrire dans `candidate.evidence.cluster_job_sources` une liste ordonnée de trois à cinq objets `{job_id, title, job_url, published_at}` ; le RPC existant copie `candidate.evidence` dans `signals.metadata_json`. Après publication, compléter `opportunities.source_urls` avec les liens uniques par PATCH filtré sur l'ID retourné, en conservant l'URL initiale ; relire les deux enregistrements. Le RPC de publication actuel n'insère que l'URL initiale dans `source_urls`, d'où cette étape explicite. Le tableau affiché doit contenir au moins le nombre d'offres nécessaire au seuil. Chaque date doit venir de l'annonce vérifiée, jamais de la collecte. Enrichir ensuite les contacts avec Perplexity selon la politique existante.

La valeur par défaut `limit=100` de l'acteur n'est pas une collecte illimitée. Trois ID regroupés ont donné 97 offres NEXTON, 2 Padoa et 1 Listen too sur 100 lignes ; cette répartition justifie un appel court par entreprise. Le prix affiché par l'acteur est par offre, mais comptabiliser le coût retourné par chaque run plutôt qu'une estimation.
